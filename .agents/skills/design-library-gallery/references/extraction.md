# 디자인 추출과 재사용 검증

## 실행 순서

사이트를 분석해 다른 화면에서도 쓸 수 있는 규칙을 만든다. 입력 구분은 스킬 본문이 소유한다. 아래 절차는 선택된 추출 요청 전체에 적용하며, 웹은 브라우저 관찰을 기본으로 한다. REA 미설치를 추출 중단 사유로 삼지 않는다.

1. **범위 고정.** URL의 실제 도착 페이지와 대표 작업을 확인한다. 별도 지정이 없으면 제공된 페이지의 주요 콘텐츠와 핵심 상호작용을 범위로 삼고 보고한다. 사이트 전체 조사로 확대하지 않는다. 기존 항목이 있으면 원본 기록을 읽고 병합한다. 이미 저장된 bookmark는 `collect`가 추출로 승격하지 않으므로 아래 승격 절차를 따른다.
2. **원본 확보.** 사용 가능한 브라우저의 공식 진입점으로 페이지를 연다. 사이트가 제공하는 디자인 시스템/브랜드 문서, 토큰/CSS 변수, 폰트와 컴포넌트 자료가 있으면 관련 부분을 읽는다. 선언만 있는 값과 현재 렌더링에 실제 쓰인 값을 구분한다. 앱/번들 분석이 필요할 때만 본문에서 안내한 REA 경로를 추가한다.
3. **렌더링 측정.** 넓은 화면과 좁은 화면에서 실제 viewport 치수를 기록한다. 렌더링/폰트 로딩을 확인한 뒤 대표 요소의 selector, computed style과 bounds를 수집한다. 제목/본문/보조문, 배경/표면/경계/강조, 주요 간격/너비, 반복 컴포넌트를 포함한다. 두 너비의 차이만으로 정확한 breakpoint를 단정하지 않는다.
4. **상태 관찰.** 실제로 있는 핵심 컴포넌트의 기본/hover/focus/active/disabled 및 메뉴/폼 등의 관련 상태를 조작한다. 빈 상태/로딩/오류는 안전하게 관찰 가능한 범위에서 확인한다. 계정 변경이나 제출을 유발하는 동작 대신 접근 가능한 상태/공식 예제를 사용한다. 못 본 상태는 관찰한 것으로 쓰지 않는다.
5. **패키지 작성.** `new`로 만든 초안에 아래 근거/커버리지와 디자인 규칙을 채운다. `new`는 크롤링이나 측정 명령이 아니다. `tokens.json`의 지원 DTCG 형식은 산출물 계약을 따르며 문서/프로토타입이 같은 토큰을 소비하게 한다.
6. **재사용 검증.** 추출한 규칙을 쓰는 작은 새 화면을 만든다. 원본과 다른 중립 콘텐츠/작업(예: 저장 항목 상세나 간단한 설정)을 택하되 원본에 존재한 컴포넌트와 밀도를 사용한다. 원본의 사진/브랜드 문구/페이지 구도를 자동 복제하지 않는다. 프로토타입에는 실제로 토큰을 읽거나 생성한 CSS를 연결한다. 원본에 없는 접근성 개선은 별도 proposed로 표시한다.
7. **비교와 보완.** 원본 대표 컴포넌트와 재사용 컴포넌트를 같은 조건에서 비교해 글꼴/간격/색상/크기 차이를 기록한다. 새 화면을 좁은/넓은 너비에서 렌더링하고 키보드 포커스, 관련 상태, 넘침과 글꼴/자산 로딩을 검사한다. 필요한 차이를 수정하고 바뀐 부분을 다시 확인한다. 코드를 썼다는 사실이나 screenshot 저장 성공으로 검증을 대신하지 않는다.
8. **검사와 열람.** 아래 완료 기준을 대조하고 `validate`를 실행한다. 모두 충족할 때만 `validate --ready` 후 ready로 표시한다. 결과가 부분이어도 읽을 수 있는 범위/한계 페이지를 미리보기로 제공한다. `view`로 로컬 갤러리를 열고 항목, DESIGN.md/토큰 링크와 새 화면이 실제 열리는지 확인한다. 반환 URL, 파일 위치, 서버 종료 방법을 보고한다. 공개 발행은 기존 승인 범위를 따른다.

## 근거와 커버리지

원본 screenshot, 소스 dump와 raw 측정 자료는 저장소가 정한 Git 무시 경로(기존 `.reference-previews/` 또는 담당 로컬 자료 경로)에 보관하고 `git check-ignore`로 확인한다. 계정 자료는 필요한 경우에만 최소 수집하며 추적 파일에 옮기지 않는다. 공개 빌드 목록에서 제외하는 것만으로 Git 커밋 노출을 막을 수는 없다.

항목의 `evidence/`에는 공개 가능한 정제된 관찰 사실/locator와 직접 생성한 새 화면 검증 자료만 두고 `reference.json`의 sources/evidence/verification에서 연결한다. 관찰 기록에는 URL/시각, viewport/테마/상태, selector/영역, 도구/방법과 확인한 값을 남긴다. 원본 캡처는 로컬 기록에서 추적하며 공개 문서에는 개인 절대 경로나 계정 데이터 대신 허용된 출처 식별자/locator를 남긴다.

| 분류 | 뜻 |
|---|---|
| `observed` | 화면/동작 또는 소스 선언에서 직접 확인. 어느 쪽인지 방법에 기록 |
| `measured` | 조건을 고정해 실제 측정한 값 |
| `inferred` | 관찰로부터 추론한 관계/규칙 |
| `proposed` | 원본에 없거나 확인하지 못해 새 화면에 제안한 규칙 |

`evidence/coverage.md`는 아래 골격으로 작성한다. 모든 행에 확인 근거 또는 구체적인 미확인/해당 없음 이유를 적는다. 단순 빈칸, “확인함”, 토큰 개수만으로 완료하지 않는다.

```markdown
# Extraction coverage v1
- Scope: 원본 URL, 대표 작업/영역, 제외한 영역
- Conditions: 관찰 시각, 두 viewport 치수, 테마, 사용 도구
- Official resources: 확인한 문서/토큰/폰트 출처 또는 찾은 범위와 미발견 결과
- Result: complete 또는 partial, 남은 한계

| 영역 | 관찰한 규칙/변형 | 근거 파일과 locator | 완료/미확인/해당 없음 및 이유 |
|---|---|---|---|
| 의미 색상과 표면 | | | |
| 타이포그래피 | | | |
| 간격/레이아웃/밀도 | | | |
| 컴포넌트와 상태 | | | |
| 좁은/넓은 화면 동작 | | | |
| 경계/반경/그림자/투명 효과 | | | |
| 모션/접근성 | | | |

| 토큰 경로 또는 별칭 그룹 | 근거 분류 | 원본 locator/측정 파일 | 사용 역할과 조건 |
|---|---|---|---|

| 새 화면 검사 | 조건 | 실행 근거 | 차이/수정/남은 한계 |
|---|---|---|---|
| 원본 대표 컴포넌트 대비 | | | |
| 넓은/좁은 viewport | | | |
| 상태/키보드/넘침/자산 | | | |
```

토큰 근거 표는 모든 원시 토큰과 의미별 별칭을 추적할 수 있게 채운다. 같은 측정에서 나온 별칭은 명시한 경로 목록/그룹으로 묶어도 된다. 모든 토큰에 독립적인 캡처를 요구하지 않는다. `reference.json`은 출처 식별과 근거 연결, coverage는 조사 범위와 대응 관계를 소유한다.

## 디자인 규칙으로 정리

- 토큰은 원시 값과 의미별 역할을 분리한다. 실제 반복값/공식 토큰 관계를 먼저 사용하고, 새로운 간격 스케일이나 semantic alias를 설계했다면 inferred/proposed로 구분한다.
- `DESIGN.md`에는 적용 범위, 선택한 토큰의 사용 조건, 레이아웃 관계/크기 제약, 대표 컴포넌트의 구성/상태, 반응형/모션/접근성 규칙, 피할 사용과 미확인 범위를 적는다. 템플릿의 제목만 채우거나 원본 CSS 전체를 붙여 넣지 않는다.
- 숫자 정본은 tokens.json이다. 문서와 새 화면에서는 토큰 이름으로 연결한다. 효과는 값뿐 아니라 배경, 레이어와 합성 조건도 설명한다.
- 사이트에 공식 시스템이 있더라도 페이지에서 확인하지 않은 전체 시스템을 추출 완료로 표시하지 않는다. 해당 페이지를 다른 화면에 재사용하는 데 필요한 관계를 설명한다.

## 완료 기준

이 기준은 새 추출 작업의 에이전트 검수 기준이다. 기존 schema/ready 기록을 소급 변경하지 않는다. CLI의 구조 검사 통과는 이 기준의 통과를 자동으로 뜻하지 않는다.

- 지정 범위의 색상/타이포그래피/간격/레이아웃과 실제 대표 컴포넌트가 모두 다뤄지고, 나머지 커버리지 행에도 근거 또는 해당 없음 이유가 있다. 적용되는 핵심 영역이 미확인이면 partial이다.
- 재사용 토큰이 실제 관찰/측정에 연결되고 원시 값/의미별 역할/제안이 구분된다. 한 개 토큰과 포괄적인 문장만 있는 결과는 범위의 규칙을 설명하지 못하므로 완료가 아니다.
- `DESIGN.md`만 읽어도 무엇에 어떤 토큰/컴포넌트를 쓰고 어떤 상태/화면에서 달라지는지 알 수 있으며, 원본의 콘텐츠와 디자인 규칙을 구분한다.
- 두 너비의 실제 원본 관찰과 새 화면 렌더링, 대표 컴포넌트 대비, 관련 상태/키보드 검증 기록이 있다. 해당 없는 상태/효과는 구체적인 이유를 기록한다.
- `validate --ready`가 통과하고 갤러리에서 문서/토큰/미리보기가 열린다. 완료 보고에는 범위와 차이, 미검증 영역을 함께 남긴다.

## 부분 결과와 기존 저장 항목

차단/인증/네트워크 실패는 정확한 URL, 실패 단계/응답과 확보한 자료를 기록한다. 공개 공식 자료나 제공된 캡처로 계속할 수 있는 부분만 작성하고 draft/partial로 표시한다. 실제 접근이 불가능하면 측정값을 채워 넣지 않는다. screenshot-only는 보이는 구성/색상 추정까지만 정리하며 폰트/숨은 상태/정확한 breakpoint/blur를 측정으로 쓰지 않는다. 사용자가 이미 준 URL 대신 캡처를 요구하고 멈추지 말고 가능한 근거와 읽을 수 있는 부분 결과를 먼저 전달한다.

기존 bookmark/note의 출처를 추출할 때는 원래 기록과 이미지를 그대로 두고, 다른 slug의 extraction 항목에서 같은 source URL을 연결한다. 원래 항목의 상세 필드/검증 이력을 산문으로 축약하거나 메타데이터를 자동 변환하지 않는다. 새 항목의 관찰/검증은 이번 실행 근거로 작성하고 기존 기록의 pass를 재사용하지 않는다. 이미 extraction 항목이면 원본을 읽고 새 근거를 병합한다.

## 투명/글래스 표면

배경 이미지와 색, 표면 불투명도, backdrop blur, 안쪽 테두리, 바깥 윤곽, 그림자, 반사 레이어를 각각 확인한다. 레이어 순서와 중간 요소의 불투명 배경/stacking context가 합성을 바꾸는지도 확인한다.

밝은/어두운 배경, 표면 중첩, 팝오버/입력창에서 같은 규칙이 유지되는지 비교한다. 투명 효과를 끈 경우의 표면과 대비를 기록한다. 일반 글래스와 실험용 Liquid Glass가 함께 있으면 서로 다른 변형으로 표시한다.

브라우저 확장, 강제 다크 모드, OS 효과가 원본과 프로토타입에 다르게 적용되는지 확인한다. 원본과 다른 환경으로 비교했다면 그 차이를 검증 기록에 남긴다.
