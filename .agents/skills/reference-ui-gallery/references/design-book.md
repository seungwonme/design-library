# 디자인 북 기록

네 장으로 큐레이션한다: UI 라이브러리, 디자인 지침, 디자인 시스템과 토큰, UI/UX 흐름. 사용자가 다시 찾을 질문을 기준으로 주 분류 하나와 태그를 정한다. 라이브러리의 나열보다 채택 이유와 적용 조건을 남긴다.

## 기록 수준 선택

- 링크, 문서, 사례를 읽고 판단을 기록하면 `note`로 시작한다. `reference.json`이 내용과 출처의 정본이며 빌드가 읽기 페이지를 생성한다.
- 실제 화면에서 값을 추출하고 새 화면까지 검증하면 기존 `new` 패키지를 사용한다. 토큰/프로토타입 계약은 그대로 따른다.
- 읽기 기록을 만들기 위해 토큰이나 실행 증거를 지어내지 않는다. 같은 대상의 추출 패키지가 있으면 출처와 사용 규칙에 병합한다.

```sh
uv --no-config run --locked --script scripts/gallery.py note <slug> --title <title> --source <url> --platform web --category guideline
```

갤러리 밖에서는 설정 참조의 전역 진입점을 사용한다. 분류와 실제 필드는 `--help`와 [빈 기록](../assets/book-template.json)을 따른다.

출처의 `access`는 읽었으면 `read`, 접근 실패면 `blocked`, 아직 시도하지 않았으면 `unread`다. 기록 전체의 `verification.level`은 `unread`, `source-read`, `hands-on`으로 별도 관리한다. 토큰 규격 문서의 분류 인자는 `--category design-system`이다.

`details`와 `flow`에는 다음 형태를 사용한다. 내용은 원문과 실제 확인 범위로 채우고, 미확인 경로는 그 사실을 값에 적는다.

```json
{
  "details": [{"label": "스택", "value": "공식 문서에서 확인한 대상 스택"}],
  "flow": [{"state": "수정 화면", "action": "답을 수정한다", "feedback": "기존 값을 보여준다", "recovery": "완료 후 확인 화면으로 돌아간다"}]
}
```

## 수집에서 기록까지

1. 기존 catalog에서 같은 대상/URL을 찾고 기존 기록을 읽는다. 한 게시물의 여러 도구는 독립적으로 평가할 때만 항목을 나눈다.
2. 사용자 링크를 출처로 보존하고 연결된 공식 문서나 저장소를 확인한다. 게시물의 인기, 가격, 성능 주장을 사실로 승격하지 않는다.
3. 읽은 출처에는 관찰 방법을, 읽지 못한 출처에는 막힌 이유를 기록한다. 대상의 내용을 확인할 출처가 없으면 초안으로 남기고 제목/본문을 추측하지 않는다. 보조 링크를 읽지 않았으면 출처별 미확인 상태를 유지한다.
4. `summary`에는 대상을, `assessment`에는 추천 이유, 사용 조건, 피할 조건, 가져올 원칙을 쓴다. 사실은 `evidence`의 원문 위치에 연결하고 해석과 적용 제안을 구분한다.
5. 아래 분야별 내용을 `details`에 기록한다. 흐름은 `flow`에 상태, 사용자 행동, 시스템 피드백, 복귀/오류 경로를 남긴다.
6. `source-read`는 문서 확인, `hands-on`은 직접 실행이다. 직접 실행에는 항목 안의 증거 파일과 확인 범위가 필요하다. 접근성/사용성/성능은 시험한 조건만 주장한다.
7. 작성이 끝나면 `validate --ready`로 검사하고 명시한 공개 파일만 빌드한다. 로컬 초안은 `build --drafts`에서 볼 수 있다. 게시물 원문, 개인 계정 화면과 원본 미디어를 자동 복제하지 않는다.

| 장 | 남길 판단 근거 |
|---|---|
| UI 라이브러리 (`library`) | 실제 패키지/프롬프트 모음/스킬의 구분, 스택, 컴포넌트 범위, 스타일 소유권, 접근성, 의존성/라이선스/유지보수 확인 범위 |
| 디자인 지침 (`guideline`) | 해결하는 문제, 규칙과 근거, 좋은 적용 예, 반례와 예외, 확인할 사용자 행동 |
| 디자인 시스템과 토큰 (`design-system`) | 원시/의미/컴포넌트 토큰 역할, 별칭, 테마와 상태, 출처 버전, 직접 추출 여부, 해당 도구의 지원 범위 |
| UI/UX 흐름 (`flow`) | 사용자 목표와 진입점, 상태 전이, 성공 기준, 빈/로딩/오류/취소/뒤로가기, 키보드와 초점, 미관찰 경로 |

## 갤러리와 재사용

장, 플랫폼, 태그와 검증 수준으로 검색한다. 문서 확인과 실행 검증을 같은 배지로 표시하지 않는다. 읽기 페이지의 값은 `reference.json`에서 생성하고 별도 HTML 사본을 편집하지 않는다.

다음 구현에 재사용할 때 대상 작업/플랫폼과 맞는 기록을 고르고 선택 이유, 옮길 원칙, 옮기지 않을 조건을 전달한다. 전달할 토큰/프로토타입이 있으면 추출 패키지의 정본을 연결한다. 제품 구현 자체는 해당 프로젝트의 구현 절차가 맡는다.

스킬 도구를 수정한 뒤 기존 갤러리에 묶음을 준비할 때는 `bundle` 계획을 확인하고 격리된 기능 worktree에서 `bundle --project-skill --apply`를 사용한다. 생성 파일의 hash를 검사한 뒤 갱신하며 push/머지/배포는 수행하지 않는다. 공개는 기존 publish/finish 승인 범위를 따른다.
